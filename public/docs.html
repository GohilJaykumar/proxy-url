SimProxy

SimProxy is a proxy simulation manager. Point it at a real upstream — an HTTP/RPC endpoint or a WebSocket server — and it hands you back an endpoint that behaves exactly like the real one until you decide it shouldn't. Break it, throttle it, make it return any error code you like, then put it back up. Your application keeps pointing at the same URL the whole time.

HTTP / RPC WebSocket Break / Fix Rate limiting Live logs Scriptable API

What is SimProxy

Testing what your app does when a dependency fails is hard. You can't take down a public RPC node, and mocks only cover the code paths you remembered to mock. SimProxy sits between your app and the real dependency, forwards traffic transparently, and lets you inject failures on demand — from the UI while you watch, or from a terminal inside an automated test.

What you can simulate

  • A total outage — every request answered with your chosen status code and message; WebSockets closed and refused.
  • Rate limiting — a hard requests-per-second ceiling that starts returning 429 once exceeded.
  • Custom error contracts — any status code (500, 503, 429, 418…) with any JSON error message.
  • Recovery — flip the same endpoint back to healthy and watch your retry and backoff logic recover.

Typical uses

  • Building and verifying error states, retries, fallbacks and reconnect logic.
  • Reproducing "the API was down" bug reports deterministically.
  • End-to-end tests (Playwright, Cypress, Jest, Vitest) that assert what the UI does during an outage.
  • Demoing resilience live: break the dependency mid-demo from a second tab.

How it works

You create a simulation: a port, the real upstream URL, and how it should fail. SimProxy starts a proxy on that port and gives you back an endpoint. Everything your app sends there is forwarded to the real upstream — until you break it.

Your app → SimProxy endpoint → real upstream
  • Break makes the endpoint fail the way you configured it. Fix makes it healthy again. Nothing restarts and the port stays bound, so your app never sees a connection refused unless you want it to.
  • Live logs from every simulation stream into the UI, and to any terminal or script that wants them.
  • Everything over HTTPS — HTTP and WebSocket simulations are served from the SimProxy domain under /proxy/<port>, so your endpoints are secure by default with nothing to configure.

Quick start

SimProxy is a hosted service — there is nothing to install or run. The web UI and the API both live at:

01 Web UI point and click, in the browser

Create a simulation

  1. Open the Create Simulation panel

    It's the first panel on the home page. Every panel can be collapsed with Minimize if you want more room.

  2. Paste the Live URL

    The real upstream you want to stand in front of:

    • https://api.example.com — an HTTP API or RPC node
    • wss://node.example.com/ws — a WebSocket server

  3. Pick the Protocol

    http or ws. It must match the Live URL — see HTTP & WebSocket for how each one fails.

  4. Choose a Port

    Anything from 1000 to 65535 that's free. Click ⚡ Suggest Port and SimProxy fills in the next available one for you.

  5. Set the failure shape

    Error Code (default 500) and Error Message are what callers receive while the simulation is broken. Enable Custom JSON response to paste a multi-field JSON error payload (with realtime syntax validation highlighting errors in red and disabling deployment until fixed). Click ⚡ Suggest Error to cycle through 10 curated error presets (500-level errors first: 500, 502, 503, 504, 507, followed by 400-level: 400, 401, 403, 404, 429), automatically updating both the Error Code and error payload.

  6. Name it (optional)

    Leave Name blank and SimProxy names it after the upstream hostname. Create a second simulation for the same host and it becomes example.com-v2, so nothing collides.

  7. Deploy Simulation

    The row appears in Running Simulations with state up. Click its Simulated Endpoint to copy it, and point your app there instead of the real URL.

✦ Keep the switch in configPut the endpoint in an environment variable (API_URL, RPC_URL…) so you can move between the real upstream and a simulation without touching code.

Break, fix & manage

The Running Simulations table is the control panel. Each row shows the id, name, type, port, simulated endpoint, live URL, state and process id, with the actions on the right.

ActionWhat happens
BreakState becomes down. Callers immediately get your error code and message (or a closed socket, for WebSocket simulations). Traffic stops reaching the real upstream.
FixState returns to up and forwarding resumes instantly. No restart, no dropped port.
DeleteStops the proxy and removes the row. The port is released.
Click the nameRename it inline — handy when several simulations share an upstream.
Click the endpointCopies it to your clipboard.

Reading the state column

StateMeaning
startingThe proxy is coming up. It becomes up within a moment.
upHealthy — forwarding to the real upstream.
downBroken on purpose. This is your doing, not a fault.
stoppedThe proxy exited. Check its terminal for the reason, then delete and recreate it.

The table scrolls internally after ten rows, so a long list never pushes the terminals off screen.

Watch live logs

  1. Tick the Terminal checkbox on a row

    A terminal card appears in the Terminal Views panel and starts streaming that simulation's output live. The checkbox in the table header selects or clears them all at once.

  2. Arrange the grid

    Use the 1 / 2 / 3 / 4 buttons in the panel header to set how many terminals sit side by side, and the height controls to make the cards taller or shorter. Both settings are remembered for next time.

  3. Read the traffic

    Each line is output straight from the proxy — forwarded requests, rate-limit rejections, connection open and close events, and a note whenever you break or fix it. Watch a terminal while you click Break to see the exact moment behaviour changes.

ℹ Streaming is on demandLogs only stream while at least one terminal is selected. Clear the checkboxes when you're done and the connection closes.
02 Terminal curl and the API, for scripts and CI

Setup & your user code

ℹ Your Sim-CodeEvery <$SIM_CODE> below is yours: loading…. Copy it from the profile icon, top right. In the browser you never need it — the UI sends it for you.

Everything the UI does is a plain HTTP call against https://proxy.leafapi.com, so the whole lifecycle is scriptable with curl, fetch, or any HTTP client. Responses are JSON. CORS is open, so browser-based test runners work too.

Your user code

Every request carries a user code in the x-user-code header. It is what makes a simulation yours: only the code that created one can list, break, fix, rename or delete it. Anyone else — including someone who guesses your port — gets a 404, as though it were not there.

How to get your Sim-Code:

  • Click the profile icon in the top-right corner of the dashboard to copy your active Sim-Code. Use this value in your MCP client config (x-user-code header or SIM_CODE environment variable), terminal scripts, or CI environment.

Codes are signed by the server, so an invented one is rejected with 401 — it cannot create anything or reach anything. Keep yours somewhere your scripts can read it (an environment variable or a CI secret) and reuse it; a new code means a new, empty workspace.

ℹ Treat it like an API keyAnyone holding your code can manage your simulations, so keep it out of commits, screenshots and shared logs. It identifies a workspace, not a person.

Check it's working

curl -s https://proxy.leafapi.com/api/version
# → {"version":"1.3.18"}

curl -s https://proxy.leafapi.com/api/simulations \
  -H "x-user-code: <$SIM_CODE>"
# → []   (a fresh code starts with nothing)

Full lifecycle

1 · Pick a port (optional)

Leave the port out and SimProxy assigns a free one — only ask for a specific port when something is hard-coded to it. When the port is taken the reply names a free one, so one call is enough either way. No Sim-Code needed. 

curl -s "https://proxy.leafapi.com/api/ports/check?port=5000"
# → {"port":5000,"available":true}
# → {"port":5000,"available":false,"suggested_port":5001}   when taken

2 · Create a simulation

# HTTP / RPC - no port given, SimProxy assigns one
curl -s -X POST https://proxy.leafapi.com/api/simulations \
  -H "Content-Type: application/json" \
  -H "x-user-code: <$SIM_CODE>" \
  -d '{
    "name": "flaky-api",
    "url_type": "http",
    "simulate_url": "https://api.example.com",
    "error_status_code": 503,
    "error_response_message": "Upstream unavailable (simulated)",
    "max_requests_per_second": 15
  }'

# WebSocket
curl -s -X POST https://proxy.leafapi.com/api/simulations \
  -H "Content-Type: application/json" \
  -H "x-user-code: <$SIM_CODE>" \
  -d '{
    "url_type": "ws",
    "port": 5002,
    "simulate_url": "wss://node.example.com/ws",
    "max_requests_per_second": 5
  }'

The response is the full simulation object, so one call gives you everything you need — the assigned port, the id, and the URL to point your app at: 

CREATED=$(curl -s -X POST https://proxy.leafapi.com/api/simulations \
  -H "Content-Type: application/json" \
  -H "x-user-code: <$SIM_CODE>" \
  -d '{"url_type":"http","simulate_url":"https://api.example.com"}')

SIM_PORT=$(echo "$CREATED"| jq -r .port)        # 5001, chosen for you
API_URL=$(echo "$CREATED" | jq -r .proxy_url)   # https://proxy.leafapi.com/proxy/5001

echo "port $SIM_PORT → $API_URL"

If you do ask for a specific port and it's taken, the error tells you what to use instead:

curl -s -X POST https://proxy.leafapi.com/api/simulations \
  -H "Content-Type: application/json" \
  -H "x-user-code: <$SIM_CODE>" \
  -d '{"url_type":"http","port":5001,"simulate_url":"https://api.example.com"}'
# → 409 {"error":"port 5001 is already in use",
#        "suggested_port":5002,"retry_with":{"port":5002}}

3 · List what you have

curl -s https://proxy.leafapi.com/api/simulations \
  -H "x-user-code: <$SIM_CODE>" \
  | jq -r '.[] | "\(.port)\t\(.name)\t\(.state)\t\(.endpoint)"'

4 · Break and fix

Address a simulation by its id or by its port — both work, and both are scoped to your code.

# break → state: down
curl -s -X POST https://proxy.leafapi.com/api/simulations/5001/down \
  -H "x-user-code: <$SIM_CODE>"

# fix → state: up
curl -s -X POST https://proxy.leafapi.com/api/simulations/5001/up \
  -H "x-user-code: <$SIM_CODE>"

5 · Rename

curl -s -X POST https://proxy.leafapi.com/api/simulations/5001 \
  -H "Content-Type: application/json" \
  -H "x-user-code: <$SIM_CODE>" \
  -d '{"name":"payments-api"}'

6 · Read the logs

curl -s https://proxy.leafapi.com/api/simulations/5001/logs \
  -H "x-user-code: <$SIM_CODE>" \
  | jq -r '.logs[] | "\(.at) [\(.stream)] \(.line)"'

7 · Delete

Deleting stops the proxy and releases the port, by id or by port number:

curl -s -X DELETE https://proxy.leafapi.com/api/simulations/5001 \
  -H "x-user-code: <$SIM_CODE>"
# → {"deleted":true,"process_termination_requested":true}

# or everything this workspace created
for port in $(curl -s https://proxy.leafapi.com/api/simulations \
              -H "x-user-code: <$SIM_CODE>" | jq -r '.[].port'); do
  curl -s -X DELETE "https://proxy.leafapi.com/api/simulations/$port" \
    -H "x-user-code: <$SIM_CODE>" > /dev/null
done
✦ Give CI its own codeCall /api/session at the start of a pipeline and use that code for the run. Everything it creates is invisible to everyone else, and "delete everything I created" at the end is then completely safe.

API reference

Base URL https://proxy.leafapi.com. JSON in, JSON out. Send x-user-code on every call except /api/session, /api/version, /api/ports/check and /api/ports/suggest, which need none.

A simulation is addressed by its port (5001) — that is what :port means in every route below. Ports are resolved among your own simulations only, so a port you do not own reads as though it were not there.

MethodPathDescription
GET/api/sessionIssues a user code. Send an existing code to have it echoed back instead of a new one.
GET/api/versionVersion of the running service. Handy as a health check.
GET/api/simulationsYour simulations.
POST/api/simulationsCreate and start a simulation. Returns 201 with the object.
POST/api/simulations/:portRename. Body { "name": "…" }. PATCH works too, for scripts already written against it.
POST/api/simulations/:port/downBreak it.
POST/api/simulations/:port/upFix it.
DELETE/api/simulations/:portStop the proxy, free the port and remove it.
GET/api/simulations/:port/logsRecent log lines for one simulation.
GET/api/ports/suggest?from=First free port at or above from. No Sim-Code needed.
GET/api/ports/check?port=Whether that one port is free. Adds suggested_port when it is not. No Sim-Code needed.
GET/api/logs/streamLive log stream (Server-Sent Events).

Error responses

StatusWhen
400Missing or invalid field — unknown url_type, port out of range, or no simulate_url.
401No user code, or one that SimProxy did not issue. Get one from /api/session.
404No simulation of yours matches that id or port. Simulations belonging to other codes are invisible, so this is also what a stranger's simulation looks like.
409The port you asked for is taken — the response carries suggested_port and retry_with so a script can resubmit straight away. Also returned if you break or fix a simulation that has stopped.
503No free port was available at all.
✦ Retry a busy port automatically409 carries suggested_port, so a script can resubmit with that port instead of failing the test run.

Streaming logs

GET /api/logs/stream is a Server-Sent Events endpoint that replays a short backlog and then pushes new lines as they happen — useful for attaching proxy traffic to a CI artefact, or asserting that a request actually reached the proxy.

QueryMeaning
idsComma-separated ports. Omit for everything in your workspace.
backlogLines replayed per simulation on connect. Default 50, max 300, 0 for live-only.

Follow from a terminal

curl -N -H "x-user-code: <$SIM_CODE>" \
  "https://proxy.leafapi.com/api/logs/stream?ids=5001&backlog=0" \
  | grep --line-buffered '^data: ' | sed -u 's/^data: //' | jq -r 'select(.line) | .line'

Capture to a file during a test run

curl -N -H "x-user-code: <$SIM_CODE>" \
  "https://proxy.leafapi.com/api/logs/stream?backlog=0" > proxy.log &
LOG_PID=$!
npm test
kill $LOG_PID

Each entry looks like this — stream is stdout, stderr or system:

{ "id": "sim-1", "name": "api.example.com",
  "stream": "stdout", "line": "Forwarding request to upstream",
  "at": "2026-09-17T09:13:02.104Z" }

A heartbeat event arrives every few seconds to keep the connection alive; skip entries without a line field.

A small helper

// tests/simproxy.ts
const BASE = process.env.SIMPROXY_URL ?? "https://proxy.leafapi.com";
let CODE = process.env.SIMPROXY_CODE ?? "";   // set one in CI, or fetch below

async function call(path: string, init: RequestInit = {}) {
  const res = await fetch(`${BASE}${path}`, {
    ...init,
    headers: { "content-type": "application/json", "x-user-code": CODE, ...init.headers },
  });
  if (!res.ok) throw new Error(`SimProxy ${path} → ${res.status} ${await res.text()}`);
  return res.json();
}

export const simproxy = {
  /* Call once before the first create if SIMPROXY_CODE is not set. */
  signIn: async () => {
    if (!CODE) CODE = (await (await fetch(`${BASE}/api/session`)).json()).user_code;
    return CODE;
  },
  create: (body: Record<string, unknown>) =>
    call("/api/simulations", { method: "POST", body: JSON.stringify(body) }),
  break: (port: number) => call(`/api/simulations/${port}/down`, { method: "POST" }),
  fix:   (port: number) => call(`/api/simulations/${port}/up`,   { method: "POST" }),
  remove:(port: number) => call(`/api/simulations/${port}`,      { method: "DELETE" }),
  /* The port itself when it is free, otherwise the free one it suggests. */
  freePort: async (port = 5000) => {
    const res = await call(`/api/ports/check?port=${port}`);
    return (res.available ? port : res.suggested_port) as number;
  },
};

The test

import { test, expect } from "@playwright/test";
import { simproxy } from "./simproxy";

let sim: { port: number; proxy_url: string };

test.beforeAll(async () => {
  await simproxy.signIn();
  sim = await simproxy.create({
    name: "checkout-api",
    url_type: "http",
    simulate_url: process.env.REAL_API_URL,      // no port: one is assigned
    error_status_code: 503,
    error_response_message: "Payments API is down (simulated)",
  });
  // start / configure your app with API_URL = sim.proxy_url
});

test.afterAll(async () => {
  await simproxy.remove(sim.port);
});

test("checkout works while the API is healthy", async ({ page }) => {
  await page.goto("/checkout");
  await expect(page.getByRole("button", { name: "Pay" })).toBeEnabled();
});

test("shows a retry banner when the API goes down", async ({ page }) => {
  await page.goto("/checkout");
  await simproxy.break(sim.port);

  await page.getByRole("button", { name: "Pay" }).click();
  await expect(page.getByText("We couldn't reach payments")).toBeVisible();

  await simproxy.fix(sim.port);
  await page.getByRole("button", { name: "Try again" }).click();
  await expect(page.getByText("Payment confirmed")).toBeVisible();
});

Testing throttling

Create the simulation with a low ceiling and the proxy starts returning 429 under load — enough to assert your backoff or your "slow down" message.

sim = await simproxy.create({
  url_type: "http", simulate_url: process.env.REAL_API_URL,
  max_requests_per_second: 2,
});

Testing a dropped WebSocket

Breaking a ws simulation closes every live socket and refuses new ones — exactly what an upstream going away looks like. Fix it and your reconnect logic should recover on its own.

test("reconnects after the socket drops", async ({ page }) => {
  await page.goto("/live");
  await expect(page.getByTestId("status")).toHaveText("connected");

  await simproxy.break(sim.port);
  await expect(page.getByTestId("status")).toHaveText("reconnecting");

  await simproxy.fix(sim.port);
  await expect(page.getByTestId("status")).toHaveText("connected", { timeout: 15_000 });
});

Wrap a test run in an outage

#!/usr/bin/env bash
set -euo pipefail

# A fresh Sim-Code for this run: nothing it creates is visible to anyone else.
# (A pipeline issues its own rather than reusing the one from your browser.)
SIM_CODE=$(curl -s https://proxy.leafapi.com/api/session | jq -r .user_code)

CREATED=$(curl -s -X POST https://proxy.leafapi.com/api/simulations \
  -H "Content-Type: application/json" \
  -H "x-user-code: $SIM_CODE" \
  -d "{\"url_type\":\"http\",\"simulate_url\":\"$REAL_API_URL\",\"error_status_code\":503}")

SIM_PORT=$(echo "$CREATED" | jq -r .port)
export API_URL=$(echo "$CREATED" | jq -r .proxy_url)

03 MCP (Model Context Protocol) Claude Desktop, Cursor IDE & VS Code

What is MCP

The Model Context Protocol (MCP) is an open standard by Anthropic that allows AI assistants (such as Claude Desktop, Cursor IDE, or VS Code Copilot) to connect directly to SimProxy. Instead of copying curl commands or manually clicking in the browser UI, your AI assistant can create, break, fix, rename, duplicate, and monitor simulations using simple natural language.

What your AI assistant can do

  • "Create an HTTP proxy for https://api.example.com with rate limit 10 req/s"
  • "Show me all my running simulations"
  • "Simulate an outage on my proxy on port 5001"
  • "Fetch recent logs from my RPC proxy"
  • "Clean up all stopped simulations"

04 Reference behaviour, limits and fixes

HTTP & WebSocket

Both share break, fix and rate limiting — the shape of the failure differs.

httpws
Upstream formhttp(s)://…ws(s)://…
Rate limit unitrequests / secondmessages / second, per connection
Over the limit429 with Retry-After: 1a 429 error message back to the client; the message is not forwarded
When brokenyour status code + JSON messageall sockets closed, new ones refused

HTTP / RPC

A transparent reverse proxy: methods, headers, bodies and streaming all pass through, with 60-second timeouts and CORS open to every origin. Self-signed upstream certificates are accepted, so internal staging hosts work without extra setup. Whole websites proxy too — HTML and CSS fetched through the gateway have their root-relative links rewritten so pages keep working; API paths are never rewritten.

WebSocket

Each client gets its own upstream connection. Authorization, cookie, origin, user-agent and forwarding headers are passed upstream, along with any subprotocol you request. Messages sent before the upstream finishes connecting are queued briefly and then delivered. Close codes and reasons from the upstream are relayed back to your client, so your reconnect logic sees the real thing.

How long a simulation lives

Every simulation holds a port, so none of them live forever. Two limits apply, whichever comes first — when either is reached the proxy is stopped, the simulation disappears and its port goes back into the pool.

LimitLengthMeasured from
Maximum lifetime24 hoursWhen it was created. It applies however busy the simulation is.
Idle timeout3 hoursThe last traffic it carried.

What counts as traffic

  • HTTP — any request that reaches the proxy, including ones it rate-limits or fails on purpose.
  • WebSocket — a new connection, or a message in either direction. An open socket that goes quiet does not count: a connection left open with no events for three hours is closed with the simulation.
ℹ Create them as you need themA simulation you set up yesterday will not be waiting for you today — making a new one takes seconds.Don't create a simulation once and hard-code its port into a suite that runs for weeks. Create it at the start of a run and delete it at the end.

Each simulation reports both deadlines, so a long-running script can tell how much time it has left: expires_at (the 24-hour cap), idle_expires_at (three hours from the last traffic) and last_activity_at.

Limits & behaviour

  • Simulations are disposable. They last at most 24 hours, and are retired after 3 hours without traffic — see how long a simulation lives.
  • A simulation belongs to one Sim-Code. No other code can list, reach, break, fix, rename or delete it, and a port taken by someone else simply reads as unavailable.
  • A stopped simulation can't be restarted. Delete it and create it again.
  • Log history is capped at a few hundred lines per simulation. Stream them if you need a full record.
  • Ports must be 1000–65535 and free on the host.
  • Rate-limit windows reset every second — a fixed window, not a sliding one, so a burst straddling a boundary can briefly exceed the nominal rate.
  • WebSocket limits count per connection, not per simulation.
  • Upstream TLS isn't verified, so self-signed staging endpoints work.
  • CORS is fully open, which is what makes browser-based test runners work.
